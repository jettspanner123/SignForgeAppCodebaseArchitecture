● On Q4 — you asked directly whether raw-JDBC-into-AssetSphere's-DB was the
  right call, so let me actually answer that rather than just filing it away:

  It's not the architecturally "best" pattern, but it's a defensible pragmatic 
  shortcut given your constraints. The concrete costs of what's there today:
  - Silent breakage risk: if anyone renames a column or table in
    AS_ConfigurationConstantTBL on the AssetSphere side, SignForge's raw SQL
    breaks at runtime with no compile-time signal — there's no contract between
    the two codebases, just a shared schema both happen to know about.
  - Bypassed business logic: if AssetSphere's own service layer does any
    validation, computed fields, or access control before exposing that data,
    this reads straight past all of it.
  - Blast-radius coupling: SignForge's backend now holds live credentials to a
    second product's database, so a SignForge compromise extends to AssetSphere
    data too.

  What makes it defensible rather than just wrong: it's read-mostly, low-change
  reference data (departments/designations/locations), one team owns both
  schemas so the coordination cost of a break is low, and you already made the
  risk-aware call to fail soft (fallback to local tables) rather than crash on
  it — that's the right mitigation given the coupling. So I'd document it as a
  genuine ADR: chosen deliberately for speed with no AssetSphere API existing,
  with the risk named explicitly and a noted future option (a thin AssetSphere
  read API) rather than presenting it as risk-free. That's more useful to a
  future agent than either pretending it's ideal or flagging it as a plain
  mistake.
